# What Changed

<div class="grid-2" style="max-width:100%;">
  <div class="card">
    <h3>Before — two human gates</h3>
    <p><span class="accent">Gate 1</span> promote: approve work into <code>Ready</code>.<br/>
    <span class="accent">Gate 2</span> merge: read and accept every PR.<br/>
    Every passing delivery still consumed human attention.</p>
  </div>
  <div class="card">
    <h3>Now — one gate + exception lane</h3>
    <p><span class="accent">Gate 1 stays human-only</span> — committing the team to build something is a judgment call.<br/>
    Routine merge: QA evidence → <span class="accent">deterministic acceptance</span> → merge controller.<br/>
    Protected or ambiguous changes still go to a human.</p>
  </div>
</div>

<br/>

- No agent seat merges — the merge controller is policy code, not a model
- Protected set: authority/policy code, merge logic, credentials, dependencies, agent instructions, security boundaries, architecture changes
- Status today: <span class="accent">designed and documented, not yet implemented</span> — the delivered code still enforces human-only merge

<!--
Why: the human gate should sit where judgment is required, not on every routine passing delivery. Readiness is a commitment decision; a routine merge with complete evidence is not.
The protected set is the honest boundary: anything that could change the rules of the system itself always reaches a human.
Do not oversell: dev and qa Consumer skills are in progress (Joanne); the acceptance evaluator and merge controller are the milestone after that.
-->

# The New QA Verification

<div class="protocol">
  <div class="protocol-step"><span class="protocol-num">1</span><strong>Claim</strong><code>[role:qa] [board-card:#N]</code><p>One PR, exact head commit.</p></div><div class="protocol-arrow">→</div>
  <div class="protocol-step"><span class="protocol-num">2</span><strong>Review</strong><code>every changed file</code><p>Design conformance, correctness, security, cross-file risk, test strength.</p></div><div class="protocol-arrow">→</div>
  <div class="protocol-step"><span class="protocol-num">3</span><strong>Challenge</strong><code>falsify findings</code><p>Each finding needs evidence and survives a refutation pass.</p></div><div class="protocol-arrow">→</div>
  <div class="protocol-step"><span class="protocol-num">4</span><strong>Verdict</strong><code>pass · fail · blocked</code><p>Structured, bound to the exact PR head.</p></div><div class="protocol-arrow">→</div>
  <div class="protocol-step"><span class="protocol-num">5</span><strong>Route by policy</strong><code>not by QA</code><p>Deterministic evaluator picks the route.</p></div>
</div>

<br/>

- Verdict and acceptance are <span class="accent">separate contracts</span> — QA publishes evidence, never selects its own route
- Line coverage is not test evidence: require branch outcomes, negative paths, behavioral assertions
- A stale verdict is invalid — new commits on the PR head void it

<!--
Step 2's dimension list is the review contract: architecture/design conformance, correctness and edge cases, complete change accounting, security and compatibility, compound cross-file risk, and test strength. Blind-spot detection repeats the affected dimension before a verdict.
Step 3 is the anti-slop mechanism: a separate pass tries to refute each material finding by checking callers, mitigations, and intended behavior. Unresolved uncertainty is recorded, never converted into a pass.
Step 5 is the separation that makes automation safe: the reviewer that produced the evidence has no authority over what happens next.
-->

# After the Verdict — Three Routes

<div class="failclass wide">
  <div><span class="fc-num">1</span><div><strong>Eligible</strong> · <code>In Review → merged → Done</code><p>Complete evidence, no protected files, checks green on the same head — the <span class="accent">merge controller</span> re-validates and merges. No human in the loop.</p></div></div>
  <div class="defect"><span class="fc-num">2</span><div><strong>Defect</strong> · <code>(In Review, qa) → (In Progress, dev)</code><p>Fix forward on the <span class="accent">same Card, same branch, same PR</span>. The findings travel in the handoff.</p></div></div>
  <div><span class="fc-num">3</span><div><strong>Protected change</strong> · <code>(In Review, human)</code><p>Policy or ambiguity requires judgment — QA states exactly which files, decision, or risk needs the human.</p></div></div>
</div>

<br/>

- Human attention moves from <span class="accent">every merge</span> to <span class="accent">only the merges that need judgment</span>

<!--
Route 1 is the new part: the controller validates the exact head SHA, required checks, and branch state itself — it does not trust the verdict blindly, and it is not an agent.
Route 2 is unchanged from the old rework loop; the invariant one Card = one PR holds through corrections.
Route 3 is the escape hatch that keeps the human in control of anything that could change the system's own rules.
-->
