  What blocked acceptance — AC4 (graceful degradation on file://) is only partially met.
  oil-map.html:36 loads the app as <script type="module" src="oil-map.js" defer>. Module scripts
  fetch in CORS mode; over file:// (origin null, no CORS headers) Chrome and Safari block the
  script, so init() never runs and showLoadError() never fires — the page is blank with no
  visible error, exactly the state AC4 forbids. It works in Firefox (permits module scripts over
  file://) and over HTTP when data files are missing.

  Why it's a spec conflict, not a dev defect

  The dev followed DD7 literally (<script type="module">). But oil-map.js has no ES module syntax
  — no import/export. The dual-load mechanism (CommonJS module.exports + the typeof module
  browser guard) works identically with a plain classic script. So type="module" is cargo-culted
  from the retired implementation and is the sole cause of the AC4 failure. Dropping it is a
  one-line change with no downside.

  My recommendation: option (a)

  Fix it properly — drop type="module". Classic scripts aren't CORS-restricted over file://, so
  init() runs, fetch() fails, showLoadError() fires, and AC4 holds in all browsers. DD7's
  dual-load still works via the typeof module guard. This costs one short dev+QA cycle (amend
  DD7, change the one line on PR #29, re-verify). Option (b) — ship as-is and scope AC4's file://
  graceful degradation to Firefox only — leaves a known blank-page gap in the two most common
  browsers for a self-inflicted reason. The file:// case is an edge (real deployment is HTTP,
  where AC4 already works fully), which makes (b) survivable but not justified given how cheap
  (a) is.
